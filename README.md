# Anas Wadi

## هيكل المشروع
```
anas-wadi/
├── wsgi.py                  # نقطة الدخول لـ gunicorn
├── requirements.txt
├── runtime.txt
├── .env.example              # المتغيرات المطلوبة — انسخها لإعدادات البيئة
└── app/
    ├── __init__.py            # app factory — يجمع كل شيء
    ├── config.py               # كل الإعدادات الثابتة (موديلات Groq، حدود الحماية...)
    ├── extensions.py           # logging + بركة اتصالات DB + Flask-Limiter + CSRFProtect
    ├── db.py                   # كل استعلامات قاعدة البيانات
    ├── security.py             # bcrypt، تعقيم المدخلات، فلتر الحقن
    ├── ai_service.py           # التكامل مع Groq (streaming، الشخصيات، الصور، الصوت)
    ├── storage.py               # تخزين دائم للصور عبر Supabase Storage
    ├── memory.py                 # ذاكرة طويلة المدى — تلخيص تلقائي للمحادثات الطويلة
    ├── rag.py                    # الذاكرة العائلية الدائمة (RAG) — تضمين محلي + pgvector
    ├── routes/
    │   ├── auth.py              # /login /register /logout /reset-password
    │   ├── pages.py             # /
    │   ├── api.py               # /api/chat (streaming)، /api/chats، /api/transcribe، /api/speak
    │   └── admin.py              # /admin — لوحة تحكم (fail-closed، ADMIN_EMAILS)
    ├── templates/
    │   ├── index.html
    │   ├── auth.html
    │   ├── admin.html
    │   └── reset_password.html
    └── static/
        ├── css/ (style.css, auth.css)
        └── js/  (app.js, auth.js)
```

## التشغيل محلياً
```bash
cp .env.example .env   # واملأ القيم
pip install -r requirements.txt
python wsgi.py
```

## النشر على Render
- Build command: `pip install -r requirements.txt`
- Start command: `gunicorn wsgi:app`
- **`gunicorn.conf.py`** (بجذر المشروع) يضبط `timeout = 300` بدل افتراضي
  Gunicorn (30 ثانية) — بدونه أي رد بث طويل (مشروع كامل، رد "مفكر"/
  "مبرمج" يستخدم أدوات مدمجة) يخلي الـworker يُقتل بمنتصف الرد.
  Gunicorn يقرأه تلقائياً، بلا حاجة لتعديل Start Command.
- أضف كل متغيرات `.env.example` في تبويب Environment.
- **FLASK_SECRET_KEY إجباري** — التطبيق يرفض الإقلاع بدونه.
- **REDIS_URL** موصى به بشدة لو أكثر من gunicorn worker — بدونه تحديد
  المعدل (rate limiting) يعمل بالذاكرة المحلية فقط ويصير غير موثوق.
- **SUPABASE_URL / SUPABASE_SERVICE_KEY** اختياريان — لتفعيل التخزين
  الدائم للصور. أنشئ يدوياً من لوحة Supabase قبل التشغيل: باكت خاص
  `chat-uploads` وباكت عام `chat-generated` (انظر `.env.example`).
- **SAMBANOVA_API_KEY / CEREBRAS_API_KEY** ⚠️ **متوقفان فعلياً عن الاستخدام
  الحقيقي** — كلاهما صار يطلب بطاقة دفع (راجع تعليق الكود بـ`config.py`
  لتفاصيل تاريخ ذلك)، فلم يعودا جزءاً من أي سلسلة فعلية رغم بقاء متغير
  البيئة قابلاً للتعيين. أُبقيا هنا فقط للتوثيق التاريخي — لا داعٍ
  لإنشائهما بعد الآن.
- **NVIDIA_API_KEY** موصى به بشدة — بلا بطاقة دفع، أنشئه مجاناً من
  `build.nvidia.com`. يُضاف كطبقة أولى (قبل OpenRouter) لعائلتي "Wadi
  3.3" و"Wadi 2.1" كلتيهما، بمفتاح مستقل تماماً عن `OPENROUTER_API_KEY`
  — راجع تعليق `NVIDIA_API_KEY` بـ`config.py` لتفاصيل الحصة والمصادر.
  بدونه، السلسلة تتخطى هذه الخطوة تلقائياً بلا أي خطأ.
- **GEMINI_API_KEY** موصى به أيضاً — بلا بطاقة دفع، أنشئه مجاناً من
  `aistudio.google.com/apikey`. طبقة ثانية (بعد NVIDIA، قبل OpenRouter)
  لنفس العائلتين، بمفتاح مستقل تماماً هو الآخر — راجع تعليق
  `GEMINI_API_KEY` بـ`config.py`. بدونه، السلسلة تتخطاها بلا أي خطأ.
- **CLOUDFLARE_API_TOKEN / CLOUDFLARE_ACCOUNT_ID** موصى به — خط الدفاع
  الأخير *العابر لكل العائلات الثلاث* (Wadi 5.4 وWadi 3.3 وWadi 2.1
  معاً)، لا مقتصر على واحدة مثل الطبقات أعلاه. بلا بطاقة دفع (10,000
  Neuron/يوم مجاناً، تتجدد 00:00 UTC). أنشئ التوكن من لوحة Cloudflare:
  Workers AI ← API ← Create Token بصلاحية **"Workers AI: Read"** فقط
  (لا حاجة صلاحيات أوسع) — ومعرّف الحساب موجود بنفس رابط اللوحة
  (`dash.cloudflare.com/<account_id>/ai/workers-ai`). راجع تعليق
  `CLOUDFLARE_*` بـ`config.py` لتفاصيل الموديل والحصة الكاملة. بدونهما
  معاً، هذه الخطوة تُستبعَد تلقائياً بلا أي خطأ — بقية السلسلة تعمل
  كالمعتاد.
- **دائرة القطع لكل مزوّد** (`app/provider_health.py`) — لو مزوّد فشل
  (429/5xx/مهلة اتصال)، يُستبعد تلقائياً من المحاولات لفترة تتصاعد مع
  تكرار الفشل (تبدأ 20 ثانية، سقفها 10 دقائق)، بدل إعادة اكتشاف نفس
  الفشل من الصفر بكل رسالة جديدة. يستخدم REDIS_URL لو مضبوط (مشترك
  بين كل gunicorn workers)، وإلا بديل بذاكرة العملية تلقائياً.

## ما تغيّر عبر المراحل
- **المرحلة 1:** ترحيل الموديلات المهجورة عند Groq، bcrypt بدل SHA-256،
  إزالة القيمة الافتراضية لمفتاح الجلسة، rate limiting على تسجيل الدخول.
- **المرحلة 2:** Flask-Limiter + Redis، connection pooling، بناء سجل
  المحادثة من قاعدة البيانات بدل الثقة بالمتصفح، حد لحجم PDF.
- **المرحلة 3:** فصل الملف الواحد الضخم لهيكل معياري كامل
  (blueprints + templates + static)، وبث حي (streaming) حقيقي للردود
  عبر Server-Sent Events بدل انتظار الرد كاملاً.
- **إصلاح لاحق:** كشف نية توليد/تحليل الصورة وسؤال الهوية — كانا يعتمدان
  على تطابق نص ساذج يخطف رسائل حقيقية غير متعلقة.
- **المرحلة 4 (جارية) — تخزين دائم للصور:** الصور المرفوعة للتحليل
  تُرفع لباكت خاص بـ Supabase Storage (روابط موقّعة مؤقتة تُولَّد من
  جديد بكل قراءة)، والصور المولّدة بالذكاء الاصطناعي تُعاد استضافتها
  بباكت عام عندنا بدل الاعتماد على استقرار pollinations.ai طويل المدى.
  كلاهما اختياري بالكامل — بدون إعداد Supabase التطبيق يعمل بالسلوك
  القديم بدون كسر أي شيء.
- **المرحلة 4 (جارية) — ذاكرة طويلة المدى:** محادثة تتجاوز 24 رسالة
  تحصل على تلخيص تلقائي متجدد (كل 12 رسالة جديدة) بدل فقدان بدايتها
  بالكامل عند تجاوز نافذة السياق. يعمل بخيط خلفي معزول تماماً عن دورة
  الرد — أي فشل بالتلخيص (شبكة، موديل، قاعدة بيانات) يُسجَّل ويُتجاهل
  بأمان على عدة مستويات حماية، ولا يمكن أن يؤخر أو يكسر رد المستخدم.
- **المرحلة 4 (جارية) — لوحة تحكم:** `/admin` يعرض أرقاماً مجمّعة
  (مستخدمين، رسائل، توزيع أوضاع، حجم يومي) — بدون أي محتوى محادثات
  فردي. الوصول **ممنوع افتراضياً للجميع** (fail-closed) إلا لبريد
  إلكتروني مضاف صراحة بـ `ADMIN_EMAILS`؛ غير المصرَّح لهم يرون 404 لا
  403 (لا نؤكد حتى وجود الصفحة). كل استعلام إحصائي محمي بشكل مستقل —
  فشل واحد لا يُسقط الباقي، والصفحة تُعرض دائماً حتى بدون بيانات.
- **المرحلة 4 — صوت (STT/TTS):** زر مايك لتحويل الكلام لنص (Whisper)
  يملأ صندوق الكتابة تلقائياً. التحويل نص→صوت (TTS عبر Orpheus) طوَّرناه
  لاحقاً بالمرحلة 5 لبث حي حقيقي بدل انتظار توليد كل المقاطع — انظر
  تفاصيله بالأسفل. مساران مستقلان تماماً عن `/api/chat` — انهيار كامل
  بأي منهما لا يمسّ الشات النصي إطلاقاً. **يتطلب خطوة يدوية بحساب Groq
  نفسه قبل ما يشتغل TTS** — راجع `.env.example`.

**✅ المرحلة 4 اكتملت بالكامل.**

- **المرحلة 5 — أدوات Groq حقيقية:** بحث ويب حي وتنفيذ كود فعلي
  (built-in tools عند Groq نفسه، `browser_search` + `code_interpreter`)
  بدل موديل يخمّن من ذاكرته. الموديل نفسه يقرر متى يحتاجها
  (`tool_choice: auto`) — لا تفعيل إجباري بكل رسالة. مجاني بالكامل،
  يشتغل فقط مع نماذج gpt-oss (كل موديلات المحادثة الحالية).
- **المرحلة 5 — ذاكرة عائلية دائمة (RAG):** وثائق ترفعها من `/admin`
  (نص + عنوان) تُقسَّم وتُحوَّل لمتجهات تضمين محلية (`sentence-transformers`،
  مجاني بالكامل بلا API خارجي) وتُخزَّن عبر `pgvector`. بكل رسالة، Wadi
  يبحث بالمعنى (لا الكلمة الحرفية) عن أقرب المقاطع ويحقنها كسياق —
  فقط لو تشابه حقيقي (عتبة 0.35) يمنع حقن معلومات غير ذات علاقة. فشل
  أي خطوة (تضمين، بحث، حتى غياب امتداد pgvector كلياً) معزول تماماً
  ولا يكسر تسجيل الدخول ولا المحادثات العادية.
- **المرحلة 5 — حصة استخدام يومية:** سقف رسائل/يوم لكل فرد عائلة
  (افتراضياً 200) يحمي مفتاح Groq المشترك من الاستنزاف — الأدمن مستثنى
  دائماً. عدّاد ذري بخطوة SQL واحدة (`UPSERT` مشروط) يمنع أي تلاعب
  حتى تحت طلبات متزامنة حقيقية.
- **المرحلة 5 — حماية CSRF كاملة:** Flask-WTF على كل التطبيق (نماذج
  ومسارات JS/fetch على حد سواء)، مع إعدادات كوكيز جلسة صريحة
  (`Secure`/`HttpOnly`/`SameSite=Lax`) وإصلاح فعّل `session.permanent`
  اللي كان معطَّلاً فعلياً من زمان (الجلسة كانت جلسة متصفح عادية بدل
  24 ساعة كما كانت النية الأصلية بـ`config.py`).
- **المرحلة 5 — استرداد كلمة مرور (بمساعدة الأدمن):** لا بريد إلكتروني
  بالمشروع، فالأدمن يولّد من `/admin` رابطاً عشوائياً (256-bit) صالحاً
  24 ساعة واستخدام واحد فقط، ويرسله يدوياً. استهلاك الرابط بخطوة SQL
  ذرية واحدة يمنع استخدامه مرتين.
- **المرحلة 5 — TTS: بث حي + وضع محادثة صوتية كامل:** `/api/speak`
  صار SSE حقيقي — الصوت يبدأ خلال أقل من ثانية بدل ثوانٍ صمت كامل
  بانتظار كل المقاطع. 6 أصوات عربية حقيقية بدل صوت واحد ثابت. تشغيل
  تلقائي للرد لو السؤال جاء بالصوت. **وضع محادثة صوتية كامل**: استماع
  بكشف صمت تلقائي (VAD) → معالجة → رد يتكلم لوحده → رجوع للاستماع،
  بلا أي زر بينهم، مع زر يدوي احتياطي دائماً متاح.
- **المرحلة 5 — تحصينات إضافية:** موديل رؤية بديل (`qwen3.8-27b`) عند
  فشل الأساسي بـ429، `ThreadPoolExecutor` محدود (2 عامل) بدل خيوط
  خام بلا حد لتلخيص المحادثات (يحمي بركة اتصالات قاعدة البيانات
  الصغيرة، 10 اتصالات بس)، وحدود جلب معقولة لاستعلامات المحادثات/الرسائل
  بدل جلب كل شيء بلا حد بكل طلب.

- **المرحلة 6 — احتياطي مجاني عبر مزوّد آخر (Meta Llama):** Groq وحده
  كان يعني: أي استنفاد لحصته المجانية (429) أو تجاوز حد التوكن لكل
  دقيقة يكسر رد المستخدم مباشرة — بالضبط الصورة اللي ظهرت بلوحة Groq
  (`console.groq.com/dashboard`). الحين، لو Groq فشل بكل نسخه (الموديل
  الأساسي + `GROQ_FALLBACK_MODEL` الداخلي)، الطلب ينتقل تلقائياً
  وبشفافية لـ`Meta-Llama-3.3-70B-Instruct` عبر SambaNova — مزوّد
  مختلف كلياً، حصته اليومية مستقلة تماماً عن Groq. الواجهة تُظهر تنبيهاً
  هادئاً (toast) لو صار هذا فعلاً، بدون قطع تدفق الرد. **ملاحظة مهمة
  للمستقبل:** موديلات Meta/Llama لم تعد مجانية عند Groq نفسه (صارت
  Enterprise فقط منذ 16 أغسطس 2026) ولا عند Cerebras (توقف تيره
  المجاني بلا بطاقة بأغسطس 2026) ولا عند OpenRouter (أزالت كل Llama
  من قائمتها المجانية مؤخراً) — راجع التعليق المطوَّل بـ`config.py`
  (قسم "مزوّد احتياطي") لتفاصيل كل مصدر. لو SambaNova توقفت هي الأخرى
  مستقبلاً، بدّل القيم هناك فقط، لا حاجة لتعديل أي كود.
- **قيد عمداً بهذه المرحلة:** الاحتياطي يغطي الشات النصي فقط (`/api/chat`)
  — الرؤية (تحليل الصور)، الصوت (STT/TTS)، وترجمة برومبت الصورة تبقى
  على Groq فقط (لا بديل مكافئ مجاني لها حالياً). ولأن Llama موديل نصي
  عادي، رد أي وضع يعتمد على أدوات Groq المدمجة (`browser_search`/
  `code_interpreter`) لن يقدر يستخدمها فعلياً لو صار الانتقال للاحتياطي
  تحديداً بتلك الرسالة — حالة نادرة جداً (فقط بعد استنفاد Groq بالكامل).

- **المرحلة 7 — مرونة حقيقية لسلسلة المزوّدين (دائرة قطع + خط ثالث):**
  الحادثة اللي بدأت هذه المرحلة: Groq (الأساسي والاحتياطي الداخلي)
  **و**SambaNova فشلا معاً لنفس الرسالة بلحظة واحدة — احتمال نادر لكن
  حصل فعلياً، وكشف فجوتين حقيقيتين: (1) لا تسجيل خادم إطلاقاً عند فشل
  كل السلسلة — سجلات Render كانت تُظهر `POST /api/chat 200` بلا أي أثر
  للمشكلة الفعلية، لأن SSE تبقى 200 بالمستوى HTTP حتى لو المحتوى نفسه
  خطأ، (2) رسالة الخطأ الخام من SambaNova (إنجليزية، تكشف اسم الموديل
  والمزوّد الداخلي) كانت تصل المستخدم كما هي بلا أي ترجمة أو تغليف.
  الحل (`app/provider_health.py` جديد كلياً + إعادة هيكلة
  `stream_chat_completion` بـ`app/ai_service.py`) مبني على أنماط
  إنتاجية حقيقية مستخدمة بأنظمة توجيه LLM فعلية (LiteLLM Router،
  Bifrost circuit breaker — راجع التعليقات المطوَّلة بأعلى
  `provider_health.py` للمصادر بالتفصيل):
  - **دائرة قطع لكل مزوّد** (Redis، أو بديل بذاكرة العملية بدونه):
    مزوّد فشل يُستبعد تلقائياً لفترة *تصاعدية* (20 ثانية → تتضاعف حتى
    سقف 10 دقائق) بدل إعادة اكتشاف نفس الفشل من الصفر بكل رسالة —
    يحل خللاً موثَّقاً بأنظمة توجيه ساذجة (إعادة محاولة مزوّد "مستنفد
    الحصة" كل دقيقة لـ24 ساعة، آلاف محاولات ضائعة).
  - **تصنيف أخطاء حقيقي:** 429 "ازدحام مؤقت" (مثال فعلي: رسالة "high
    demand" اللي وصلت فعلياً بالتقرير) يستاهل إعادة محاولة فورية واحدة
    بنفس المزوّد؛ 429 "حصة منتهية"/5xx/مهلة اتصال تنتقل للمزوّد التالي
    مباشرة بلا إهدار وقت؛ دائرة القطع نفسها تُفعَّل فقط لأعطال "صحة
    المزوّد" الحقيقية (429/5xx/401/403) لا لأخطاء طلب محدَّد (400) حتى
    لا نعطّل مزوّداً سليماً بسبب رسالة واحدة غريبة.
  - **خط احتياطي ثالث (Cerebras)** — معطَّل افتراضياً (`CEREBRAS_API_KEY`
    فارغ = صفر تغيير بالسلوك)، يقلّل احتمال تزامن فشل كل المزوّدين معاً
    مستقبلاً. راجع تحذير الصدق بـ`config.py` عن حالته المتضاربة حالياً.
  - **رسالة خطأ عربية موحَّدة نهائية** بدل أي نص خام من أي مزوّد — التفاصيل
    التقنية الكاملة مسجَّلة بـ`log.error` لكل خطوة فشلت (يحل الفجوة الأولى).
  - **حماية من رد مخلوط:** لو مزوّد انقطع *بعد* إرسال محتوى فعلي للمستخدم،
    لا تبديل لمزوّد آخر (كان سينتج رداً بنصفين من مصدرين مختلفين تماماً —
    خلل كان موجوداً بالتصميم القديم أيضاً، أُصلح هنا كأثر جانبي).
  - **اختبار تكامل حقيقي** (`tests/test_provider_chain.py`) يشغّل
    `app/ai_service.py` و`app/provider_health.py` الفعليين (لا نسخة
    مبسَّطة) مع تزييف `requests.post` فقط — يغطي أربعة سيناريوهات:
    نفس حادثة التقرير بالضبط، فشل كل السلسلة (يتحقق عدم تسرّب نص خام)،
    دائرة القطع (يتحقق تخطي مزوّد مبرَّد بلا أي اتصال HTTP فعلي)، ورد
    مخلوط. أول اختبار آلي محفوظ فعلياً بالريبو — يغطي جزئياً بند
    "اختبار آلي" بخارطة الطريق أدناه (CI نفسه لسا غير موجود).

- **المرحلة 8 — اختيار عائلة الموديل + تثبيت الوضع لكل محادثة:**
  ثلاث تعديلات مترابطة على تجربة الاختيار:
  - **حذف قائمة "+" (لخص/ايميل/ترجم/شرح/مشروع كامل/API/صلح Bug):**
    كانت تُدرج نصاً جاهزاً بمربع الكتابة فقط — لا شيء يفعله المستخدم
    بنفس الطلب مباشرة لا يفعله كتابته يدوياً، فكانت مجرد ديكور واجهة
    بلا وظيفة إضافية فعلية.
  - **اختيار عائلة الموديل صراحة (Wadi 5.4 / Wadi 3.3)** — زر جديد
    بمكان قائمة "+" القديمة، بنفس مكانها. Wadi 5.4 = سلسلة Groq
    الكاملة بكل احتياطها التلقائي من المرحلة 7 (Groq ← Groq احتياطي ←
    SambaNova ← Cerebras)؛ Wadi 3.3 = تروح *مباشرة* لعائلة
    SambaNova/Cerebras بلا أي محاولة على Groq إطلاقاً — احترام صريح
    لاختيار المستخدم، لا "احتياطي عن احتياطي". Wadi 3.3 لا يدعم
    البحث الحي أو تنفيذ الكود المدمجين (تعملان فقط مع gpt-oss عند
    Groq) — مذكور بالواجهة نفسها تحت الخيار.
  - **مودال احترافي عند التبديل التلقائي** (بدل toast هادئ سابقاً):
    لو Wadi 5.4 استُنفد فعلياً وانتقلنا تلقائياً لـWadi 3.3، يظهر
    مودال يوضّح هذا صراحة + تقدير زمني ودّي لعودة Wadi 5.4 (`app/ai_service.py`
    يمرر `retry_after` **الحقيقي** من رأس `Retry-After` اللي أرسله Groq
    نفسه مع آخر فشل — لا رقم ثابت مخترَع — والواجهة تصيغه بعربية سليمة
    نحوياً: دقيقة/دقيقتين/دقائق/ساعة/ساعتين/ساعات حسب القيمة). يظهر
    مرة واحدة بالضبط لكل رسالة تبديل (لا يتكرر لكل خطوة داخلية بنفس
    العائلة الاحتياطية)، وأبداً عند اختيار Wadi 3.3 صراحة من البداية
    (لم يكن "احتياطياً" وقتها، كان الاختيار المقصود).
  - **تثبيت الوضع (سريع/مفكر/مبرمج...) وعائلة الموديل لعمر كل محادثة:**
    يُختاران بحرّية فقط قبل أول رسالة — بعدها الواجهة تعطّل الزرّين
    (نفس مبدأ اختيار موديل بمحادثات كلود). **التطبيق الفعلي من طرف
    الخادم نفسه** لا الواجهة فقط: `get_chat_locked_settings` بـ`db.py`
    (عمود `model_family` جديد + `mode` الموجود أصلاً) يقرأ إعدادات
    *أول* رسالة بكل `chat_id` ويفرضها على أي طلب لاحق بنفس المحادثة،
    بغض النظر عمّا يرسله الطلب نفسه — لا يمكن تجاوز القفل بطلب API
    مباشر. فتح محادثة قديمة يعكس تلقائياً الوضع/العائلة المستخدَمين
    فعلياً بها (لا آخر اختيار عام بالمتصفح).

- **المرحلة 9 — عائلة "Wadi 3.3" تنتقل لـOpenRouter ثم تتقوّى (سبتمبر 2026):**
  المرحلتان 6-8 أعلاه وثّقتا "Wadi 3.3" كسلسلة SambaNova ← Cerebras —
  الاثنان صارا يطلبان بطاقة دفع فعلياً (راجع تحذير الصدق المطوَّل بـ
  `config.py`)، فانتقلت العائلة لنفس مزوّد OpenRouter المستخدم أصلاً
  بـ"Wadi 2.1" (المرحلة 8 أعلاه)، بموديلين مختلفين عمداً عن موديلَي
  تلك العائلة حتى تبقى تجربة مختلفة فعلياً لا نفس الرد بتسمية أخرى —
  بلا أي تعديل بمنطق `_build_provider_chain` نفسه (نفس مبدأ "غيّر
  القيمة بـ`config.py` فقط" المتّبع بكل تبديل موديل سابق بهذا المشروع).
  لاحقاً (13 سبتمبر 2026) استُبدل الموديلان الأولان هناك (Nemotron 3
  Super + Ling 3.0 Flash VL) بموديلين أقوى فعلياً من نفس قائمة "Top
  Free Models" الحيّة بلا بطاقة (Dots3-Note Preview + Nemotron 3.5
  Lightning) — سياق أكبر، استخدام فعلي أعلى، وتغطية أعم لأوضاع Wadi
  المختلفة لا تخصص ضيق ببرمجة فقط. التفاصيل الكاملة وسبب الاختيار
  بـ`config.py` (قسم "عائلة Wadi 3.3"). أُصلح أيضاً `tests/test_provider_chain.py`
  الذي بقي يحاكي السلسلة القديمة (SambaNova/Cerebras) رغم أن الكود
  الفعلي انتقل لـOpenRouter منذ فترة — كان سيفشل بـ`AttributeError`
  فوراً عند أي تشغيل فعلي.

## المتبقي من خارطة الطريق
- تطبيق موبايل عبر Expo، نموذج استدامة مالية (خارطة الطريق الأصلية).
- CI فعلي بالمشروع (GitHub Actions أو مشابه) يشغّل `tests/` تلقائياً
  بكل push — أول اختبار آلي محفوظ بالريبو من المرحلة 7 أعلاه، لكن لا
  شيء يشغّله تلقائياً بعد.
- Observability حقيقي (Sentry أو مشابه)، وحذف حساب/تصدير بيانات
  للمستخدم نفسه.
- (اختياري) كود دعوة للتسجيل — أُجِّل عمداً: الرابط يُشارَك فقط مع
  عائلة/أصدقاء مقرَّبين حالياً.
- (اختياري متقدم) تخصيص نموذج ضيق بـQLoRA لمهمة محدَّدة جداً — يحتاج
  تحديد المجال أولاً.
